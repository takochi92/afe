# 第1部　ブログを検索に出す方法（SEO）

## 1-1　Google Search Consoleの登録とサイトマップ送信（オーナーの操作）

Search Consoleは、Googleが無料で出している「自分のサイトがGoogleにどう見えているか」を確認する道具です。登録しないと、検索に出ているかどうかも分かりません。

**先に知っておくこと**
- 画面の名前や場所は、Google側で変わることがあります。止まったら、画面をスクリーンショットで送ってください。案内し直します。
- 私たち（AI）は、Search Consoleにログインできません。ログインと送信はオーナーの操作です。
- 「所有権の確認」に使う文字列は、パスワードではありません。チャットに貼って大丈夫です（ただし、他のトークンや鍵は貼らない）。

**操作の手順（オーナー）**
1. パソコンかスマホで、普段使うGoogleアカウントにログインする（会社用に分けたいなら、そのアカウント）。
2. https://search.google.com/search-console を開く。
3. 「プロパティを追加」を押す。2つの選択肢が出たら、右側の**「URLプレフィックス」**を選ぶ。
   - 左の「ドメイン」は、ドメインの設定（DNS）を触る方式。いまのサイトは無料の workers.dev なので、使えないと思われる（未確認）。
4. 入力欄に次のアドレスを、そのまま入れて「続行」を押す。
   `https://kodomo-okane-note.site-kanri19.workers.dev`
5. 「所有権の確認」の画面になる。確認方法の一覧から**「HTMLタグ」**を選ぶ。
6. `<meta name="google-site-verification" content="ここに長い文字列">` と出る。**「content=」の引用符の中の文字列だけ**をコピーして、チャットで社長に送る。
7. （社長の作業）社長が `blog/site.json` にその文字列を足し、サイトを作り直して公開する。公開されるまで、数分〜少し待つ。オーナーは「公開した」と返事が来るまで次に進まない。
8. Search Consoleの画面に戻って、**「確認」**を押す。「所有権を確認しました」と出れば成功。「プロパティに移動」を押す。
   - 失敗したときは、公開から数分待ってもう一度。それでも失敗なら、画面を送る。
   - 確認用のタグは、あとで消してはいけない（消すと確認が外れる）。社長が残す。
9. 左のメニューから**「サイトマップ」**を開く。「新しいサイトマップの追加」の欄に `sitemap.xml` と入れて**「送信」**を押す。
   - 送信後、表の「ステータス」が「成功しました」になればよい。最初は「保留中」や「取得できませんでした」と出ることもある。数時間〜1日おいて見直す。続くなら画面を送る。
10. 画面上部の検索窓に、記事のアドレスを1本ずつ貼って Enter（「URL検査」）。結果の画面の**「インデックス登録をリクエスト」**を押す。やるのは次の5つ。
    - トップ `https://kodomo-okane-note.site-kanri19.workers.dev/`
    - `/oya-kouza-betsu-kaisha/` ／ `/kyodai-futari-ijo/` ／ `/junior-nisa-tigai/` ／ `/haraidashi-12sai/`
    - 「URLがGoogleに登録されていません」と出るのは、公開直後は珍しくない。リクエストは何度も押さなくてよい。1日に押せる回数に上限があるが、数は未確認。
    - リクエストしても、必ず載る保証はない。Google公式も「通常は1日程度」としているだけ（research/20261010-traffic-plan.md）。
11. 数日〜1週間後に、もう一度開く。見る場所は次の2つ。
    - 「ページ」（インデックス作成）: 「登録済み」の数
    - 「検索パフォーマンス」: 「合計表示回数」「合計クリック数」と、下の「クエリ」の一覧
    - 最初は0でもおかしくない。数字が出たら、画面のスクリーンショットをチャットに送る（毎週1回）。
12. 新しい記事を公開したら、社長が「公開した」とお知らせする。オーナーは手順10と同じやり方で、その記事のアドレスだけリクエストする（週に2回、まとめてでよい）。

**もう一つの注意**
- 手順3〜12は、すべてGoogleの無料機能。お金はかからない。
- Bing（マイクロソフトの検索）の同様の道具もあるが、今回は調べていない（未調査）。後回しにする。

### 足りない点と、社長が行う修正（優先度順）
優先度 A＝1週目にやる ／ B＝2〜3週目 ／ C＝余裕があれば

| # | 優先 | 足りない点 | 具体的な変更（社長が行う） | 理由 |
|---|---|---|---|---|
| C1 | A | Search Consoleの所有権確認用タグがない | `site.json` に `"googleSiteVerification": ""` を追加。`layout()` の `<head>` に、値があるときだけ `<meta name="google-site-verification" content="…">` を出す | 手順1-1の7番に必要 |
| C2 | A | sitemapに `lastmod`（最終更新日）がない | `sitemap.xml` の各 `<url>` に `<lastmod>`（記事・固定ページは `meta.updated`、トップは記事の中で一番新しい `updated`）を足す。**中身を本当に変えたときだけ `updated` を変える**運用にする | Googleに更新を伝える材料になる。ごまかしの更新日は付けない |
| C3 | A | 404ページに `noindex` がなく、`description` が空 | 404の `<head>` に `<meta name="robots" content="noindex">` を出し、説明文を入れる。あわせて、存在しないアドレスが本当に404（ステータス）を返すか確認する（200で返す「ソフト404」だと検索の評価によくない）。Cloudflareの設定は**未確認**なので、公開後に確かめる | 空ページが検索に出るのを防ぐ |
| C4 | A | 共有時の表示（OGP）がない | `<head>` に `og:type`（記事は article、他は website）、`og:title`、`og:description`、`og:url`（canonicalと同じ）、`og:site_name`、`og:locale`（ja_JP）、`og:image`、`twitter:card`（summary_large_image）を追加。画像は1200×630の1枚を `public/img/ogp.png` に用意する（`scripts/make_card.js` などで作る） | 誰かがリンクを共有したとき、見た目が整う。検索順位に効くかは未確認 |
| C5 | A | ファビコン（タブや検索結果の小さい画像）がない | `public/` に正方形のアイコンを置き、`<link rel="icon">` と `apple-touch-icon` を追加。元は `assets/profile/icon.png`（1080×1080）。大きさの条件はGoogleの公式で確認してから作る（**未確認**） | 検索結果にサイトの印が出る可能性がある（出るかはGoogle次第） |
| C6 | B | 記事の構造化データが薄い | `Article` に次を追加: `mainEntityOfPage`（記事のURL）、`url`、`image`（OGP画像）、`author` に `url`（`/about/`）。`author` は今のまま「組織＝こどものお金ノート」で、**個人名や肩書きは作らない**（research/20261011-blog-plan.md） | Googleの推奨項目。表示が変わる保証はない |
| C7 | B | サイト名・パンくずの構造化データがない | トップに `WebSite`（`name`、`url`）を出す。記事に `BreadcrumbList`（ホーム → 記事名）を出す。画面にも「ホーム > 記事名」を表示する | 検索結果にサイト名が出やすくなる可能性（Google次第） |
| C8 | B | 内部リンクが弱い（下の1-4で説明） | 記事の先頭に `related: slug1,slug2` を書けるようにして、本文の下に「あわせて読みたい」（記事名つきのリンク）を自動表示する。ホームへ戻るパンくずも付ける | 記事同士のつながりを作る |
| C9 | B | 記事4本のうち、タイトルが長めのものがある | 下の「タイトルの見直し案」参照。直したら検品部が確認し、`updated` を変える | 検索結果でタイトルが途中で切れることがある（切れる文字数は未確認。推測として前半30字前後に大事な言葉を置く） |
| C10 | B | 外部リンクがすべて `nofollow` | 公的資料・各社の公式ページへのリンクは `rel="noopener"` のみに。ASPのリンクだけ `rel="sponsored nofollow noopener"` にする（`site.json` に `sponsoredHosts` の一覧を持たせて判定）。**案件リンクを置く前に必ず直す** | 広告リンクを正しく示すため。公式資料への `nofollow` が順位に悪いかは未確認 |
| C11 | C | RSSに日付がない | `rss.xml` の各 `<item>` に `<pubDate>` と `<guid>` を追加 | 読み取りソフト向け |
| C12 | C | 大きな画像を使うときの指定がない | `<meta name="robots" content="max-image-preview:large">` を追加。Googleディスカバー向け。公式資料（traffic-plan記載のURL）で必要性を確かめてから。ディスカバーは「副産物」扱いで、狙って作らない | ディスカバーに出るかは読めない |
| C13 | C | アクセス解析がない | Googleアナリティクス（GA4）か、Cloudflareの簡易解析を入れるか、オーナーが決める（末尾の質問）。入れるなら、プライバシーのページに追記が必要（現在の内容は未確認。社長が確認） | SNSからの来訪者を、見えるようにするため |

## 1-4　内部リンクの方針

いまの記事4本のつながりは、「親・別の会社 ⇄ 兄弟」「ジュニアNISA ⇄ 払出し」の2組だけです。トップの一覧が、事実上の目次になっています。

**方針**
1. 全記事に「関連記事」を2本以上付ける（C8の自動表示を使う）。新しい記事を出したら、関係の深い既存記事にも1行足して、行き来できるようにする。
2. リンクの文字は、「こちら」ではなく、**記事の内容が分かる言葉**にする（例：「親が別の証券会社に口座を持っている場合」）。
3. 記事の流れは、「悩み解決 → 比較・手順 → （提携後）案件」。逆走させない（悩み解決の記事に、いきなり案件リンクを置かない）。
4. トップページへ戻るパンくず（C7）を付ける。
5. 近い話題どうしは束ねる。当面の束は次のとおり（research/20261011-blog-plan.md の案を、いまの4本に当てはめた）。
   - 申込・口座の選び方: 親が別の会社、兄弟、（これから）事前申込の比較、楽天とSBI、変更できない選び方
   - 制度のしくみ: ジュニアNISAの違い、払出し、（これから）積立設定
   - 家族の形: 兄弟、新生児、口座管理者
6. 制度のまとめ（ハブ）の記事は、記事が10本ほどそろってから作る（大きなKWの順位は当面狙わない）。
7. 同じ内容の記事を、言い回しだけ変えて量産しない（スパムの扱いになりうる。research/20261011-blog-plan.md）。

## 1-5　workers.dev（ドメインなし）の限界と、独自ドメインに切り替える判断の目安

**いまの状況**: `kodomo-okane-note.site-kanri19.workers.dev`。無料で、費用はかからない。オーナーの決定（2026-10-11）で、様子を見ながら進めている。

## 2-1　実績のない新しいアカウントがやること

### (1) 保存されやすい形式
docs/instagram-flow.md の方針に、次を足します。
- 枚数は5〜6枚から。1枚目は問いかけ＋数字（例：「こどもNISA 事前申込、知ってた？」）。煽りの言葉は使わない。
- 1枚に1つのポイント。最後の1枚は「まとめ＋保存して、あとで見返してね」。
- **チェックリスト型・比較表型・手順型**は、見返したくなる形と思われる（推測）。1本の記事から、1つの図解にする。
- 毎回同じ見た目（黄×赤、キャラクター）にして、「このアカウントの投稿」と分かるようにする（docs/profile.md、docs/characters.md）。
- 全枚に「時点」と「元本割れのリスク」の注記を入れる（現状の自動フッターのまま）。
- 1行目（キャプションの冒頭）に、検索される言葉を自然に入れる（例：「こどもNISA 兄弟」）。Instagramの公開投稿がGoogle検索に載るようになったという報道がある（二次情報。research/20261010-traffic-plan.md）。無理に詰め込まない。
- 同じ画像は、ThreadsとInstagramで使い回してよい（docs/instagram-flow.md）。**文章は変える。**

### (2) 投稿の頻度と時間帯
| 項目 | 方針 |
|---|---|
| 回数 | 1日の上限は3件（現行ルール）。ただし**質を保てる範囲で**。Instagramのカルーセルは、まず週3本を目安（research/20261010-traffic-plan.md の計画）。Threadsは毎日 |
| 時間帯 | 現行の朝8:07・昼12:26・夕19:41（日本時間）を**最初の2週間は変えない** |
| 最適な時間 | 未確認。ThreadsとInstagramのインサイト（分析画面）に「フォロワーが見ている時間」が出るか、新規アカウントで出るかは未確認。3週目に、時間帯ごとの閲覧数・保存数を比べて決める。件数が少ないうちは、差が偶然かもしれないので決めつけない |
| 記事の公開日 | 記事を公開した日に、図解（Instagram＋Threads）を出す（traffic-plan の勝ち筋） |

### (3) プロフィールの導線
- リンク欄に、ブログのアドレス（設置済み、docs/profile.md）。投稿文にURLは書かない。
- 表示名「こどもNISAやさしく図解」はそのまま（検索される言葉を含む）。
- プロフィール文の追加案（オーナーが手で入れる。いまの文Aは短いので余裕がある）:
  「…広告（PR）を含む場合は明記します。**詳しい記事はプロフィールのリンクのブログへ。**」
- ストーリーズやハイライトに「ブログ記事の一覧」を作ると、リンクの置き場所が増える（Instagramのストーリーズのリンクは使える。research/20261010-kodomo-nisa.md の B-4）。**ただしリンクの新しい掲載は、オーナーの許可の範囲か確認が必要**（CLAUDE.md）。やるなら、オーナーが「やってよい」と返事をしてから、オーナーが操作する。
- 投稿を「固定」して、最初に見せたい投稿を上に置く機能が使えるかは、画面で確認する（未確認）。
- ブログへ行った人が迷わないよう、トップの記事一覧のわかりやすさを保つ（C8のパンくず・関連記事）。

### (4) ハッシュタグ
- 効果的な数・種類は**未確認**（追加リサーチ依頼）。Threadsにはタグの扱いが独自の仕様である可能性があるが、これも未確認。
- 当面の方針: 内容に合った言葉を**少なめ**に付けて、保存・リーチを比べる（例：#こどもNISA #新NISA #子育てのお金 のように、内容に合うもの）。
- 付けないもの: #お得 #最強 #絶対 などの煽り、特定の証券会社名のタグ（宣伝に見えるため）、広告表記をタグの中に紛れ込ませること（docs/compliance.md 第1項。「#PR」だけを他のタグに混ぜて隠すのは不可）。

### (5) コメント・返信の扱い
- **お金の相談には、個別の助言をしない**。「どこがいいですか」と聞かれたら、会社をすすめず、「条件は会社ごとに違うので、公式ページで確認を」と案内し、関連するブログ記事の名前を伝える。外務行為（勧誘・個別商品の説明）は禁止（research/20261010-kodomo-nisa.md の B-3）。
- 返信の内容は、docs/compliance.md の基準で下書きを作り、検品部が確認する。
- 返信が自動でできるかは未確認（Metaの許可の範囲が分からない）。**自動返信は、オーナーの許可が出るまでしない**（新しい種類の操作）。当面は、私たちが返信案を作り、オーナーが手で返す形にする。
- 荒らし・宣伝コメント・DMでの勧誘は、返信せず、非表示や報告の機能を使う（オーナー操作）。
- 他人の投稿への返信（交流）は、事実を補う内容だけにする。リンクや宣伝は書かない。自動化はしない。
- ThreadsのコミュニティはJapanでも導入が発表された（2026年6月、Impress Watch。research/20261010-traffic-plan.md）。使えるか、規約の範囲で試せるか、オーナーに確認してから（2週目以降）。

## 2-2　ブログへの導線の作り方

**基本の流れ**: SNSの投稿（役に立つ情報） → プロフィール → リンク欄のブログ → 記事。アフィリエイトのリンクは**ブログにだけ**置く。SNSにはASPのリンクを置かない（research/20261010-traffic-plan.md）。

### 「プロフィールから詳しい記事へ」の一文は入れてよいか
**結論: 条件つきで可。**（法律の判断ではなく、社内ルールにもとづく考え方。迷ったらオーナーに確認）

**根拠**
- 規約: Instagramの投稿のキャプションのURLは押せないので、プロフィールへ案内するのは普通のやり方。ThreadsとInstagramで「プロフィールのリンクへ案内する文」を禁止する規約は、今回の調査では見つからなかった。ただし、Metaの公式文言の確認は**未確認**（追加リサーチ依頼）。
- 社内ルール: 「リンクは投稿に載せない」「迷う内容はオーナーに確認」（docs/instagram-flow.md、CLAUDE.md）。プロフィールのリンク欄は、オーナーが許可して設置済み（docs/profile.md）。一文はリンクそのものではない。
- 広告の決まり: SNSの投稿自体は広告ではない、ただし**リンク先の記事にPRが含まれることをプロフィールに明記しておくのが安全**という考え方（research/20261010-traffic-plan.md の「解釈」）。ステマ規制（景品表示法）は、広告であることが分かりにくいのを問題にする（docs/compliance.md 第1項）。

**条件**
1. 一文は、**事実の案内だけ**にする。口座開設や申込を急がせない。
2. 一文を、全部の投稿に入れない。**対応する記事があるときだけ**。同じ文の連投にならないよう、言い回しを変える。
3. 記事名を入れて、どの記事か分かるようにする（トップの一覧で探せる）。
4. 「こちら」「下のリンク」とは書かない（投稿にリンクはないため）。
5. **最初のアフィリエイトリンクを置いた日から**: 紹介する記事にPRが含まれる可能性がある投稿には、「※リンク先の記事には広告（PR）を含む場合があります」を、本文にはっきり書く（タグに紛れ込ませない）。プロフィール文の「広告（PR）を含む場合は明記します」も残す。
6. 紹介する記事で、特定の会社をすすめない。

**例**
| 区分 | 文 |
|---|---|
| OK | 「くわしい手順は、プロフィールのリンクのブログにある『親が別の証券会社の場合』の記事にまとめています。」 |
| OK（案件リンク設置後） | 「…記事にまとめています。※リンク先の記事には広告（PR）を含む場合があります。」 |
| NG | 「今すぐプロフィールから申し込もう！」「お得なキャンペーンはプロフィールのリンクから」「プロフィールから口座開設」（勧誘・煽り） |
| NG | 全部の投稿の最後に、同じ一文をそのまま入れる |

**計測**: プロフィールのリンクのタップ数は、各アプリのインサイトで見る（表示の名前は画面で確認。未確認）。ブログ側で「SNSから来た」を見分けるには、アクセス解析が要る（C13）。リンク欄に `?utm_source=threads` のような印を付ける案もあるが、リンクの変更になるため、オーナーに確認してから（docs/profile.md はリンク欄の文字を決めている）。

# 追加リサーチ依頼（リサーチ部へ）
1. 新生児・時期別の申込（各社の公式資料）／口座管理者の定義と手続き／事前申込の必要書類の再確認／積立のみ（一括不可）の根拠の再確認／楽天・SBIの受付内容の再確認
2. Google Search Consoleの最新手順（URLプレフィックス、workers.devのドメインの扱い、インデックス登録リクエストの上限、サイトマップのエラー対処）
3. Googleのファビコン・サイト名・Articleの構造化データの推奨項目、`max-image-preview` の要否
4. Cloudflare（Workers）での、存在しないURLの404の返し方、転送（301）の設定方法、独自ドメインに移すときの旧アドレスの扱い、簡易アクセス解析の使えるか
5. Threads・Instagramのハッシュタグの仕様と、新規アカウントの推奨される使い方／ThreadsとInstagramで「プロフィールのリンクへ案内する文」に関するMeta公式の考え方／返信をAPIで扱える許可の範囲
6. 検索ボリュームを調べる無料の方法とその条件（キーワードプランナー等の費用・登録条件）
7. 営業部へ: SNSから自社記事へ誘導し、記事内のリンクから成果が出る形が、各ASP・広告主の規約で問題ないか（research/20261010-traffic-plan.md の(a)）。静的サイト・独自ドメインなしで審査に通るか（blog-plan の(f)）

# 執筆上の注意（この企画に関連する記事・投稿すべて）
- 冒頭のPR表記（広告を含む記事のみ）。案件リンクは**提携済みになってから**
- 「YYYY年MM月時点」を付ける。確認できていないことは「未確認」と書く
- 金融（YMYL）: 個別商品の推奨・利回りの断定をしない。試算には「仮定・元本保証なし」
- 税の話（贈与税・名義預金）は、監修が決まるまで出さない
- 効果の数字（○％増える等）は、根拠がない限り書かない
- 外部への送信・登録は、すべてオーナーの操作
