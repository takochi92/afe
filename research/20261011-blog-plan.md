### 1-2. 「AIが全自動で公開できるか」の観点（最重要）

**① 静的サイト**
- 仕組み：記事は Markdown。AI（社長／執筆部）がリポジトリに git push → Cloudflare がビルドして公開。検品に合格した記事だけ main に入れる運用にすれば、既存の「drafts → 検品 → published」の流れとそのまま重なる。
- 必要な通信先：**github.com（git push。Threads用の `takochi92/afe-assets` で既に使っている経路と同じ）**。Cloudflare 側は、オーナーが最初に GitHub と連携するだけで、AIは Cloudflare に触らない。
- 秘密情報：**新しいトークンは不要**（push 権限は `add_repo` で付与する既存の仕組み）。直接デプロイ（wrangler）を使う場合だけ `api.cloudflare.com` と API トークンが要る（その場合は環境のネットワークシークレットに登録し、値は見えない・書かない・ログに出さない運用）が、今回は不要。
- 注意：Cloudflare は、新規プロジェクトには Pages ではなく Workers（Static Assets）を使うよう公式に案内している。Pages は動作するが新機能は Workers に集中（終了日は確認できず）。設定は Workers 側で行うのが無難。
- 注意：GitHub Pages は上記の商用規定により避ける。

**② WordPress（レンタルサーバー）**
- 仕組み：WordPress 5.6 以降の標準機能「アプリケーションパスワード」を使い、`/wp-json/wp/v2/posts` に POST して投稿（公式）。パスワードは発行時に一度しか表示されない。通常のログインパスワードは使えない。
- 必要な通信先：**自サイトのドメイン（例：example.com）**。この環境は許可ドメイン制なので、**オーナー（または管理者）がドメインを許可リストに追加する必要がある**。
- 秘密情報：アプリケーションパスワードを環境のネットワークシークレットに登録する。ただし認証は Basic 認証。Threads は Bearer を自動付与しているが、**Basic 認証のヘッダーを環境のシークレット機能で付けられるかは未確認** → 管理者に要確認。
- 落とし穴（エックスサーバーの公式FAQ・マニュアルより）：「REST API アクセス制限」（国外からの接続を制限）は**デフォルトで有効**。AIの実行環境が日本国外にある場合は 403 になりうる。ほかに WAF の誤検知、シンプルWAF、CloudSecure WP Security による REST API の無効化でも止まる。設定を一つずつ切り替えて検証する必要がある。
- 公開前の確認を挟みたいなら、`status: draft` で投稿し、公開は人または社長が行う運用にできる（WordPress標準の仕様）。

**③ WordPress.com**：REST API は Business プランの開発者向け機能として記載されている。プラグインは有料プランで入れられるとする記載もあり、検索結果だけでは食い違う → **要確認**。OAuth等の認証方式と通信先ドメインも未確認。

**④ はてなブログ**：公式に AtomPub（記事の投稿・編集・削除）がある。使うには詳細設定で AtomPub を有効にする。通信先は `blog.hatena.ne.jp` と推測（**要確認**）。広告掲載は個人営利利用として可だが、証券案件の審査は**要営業確認**。独自ドメインには Pro が必要。**本拠地にはせず**、保留（前回資料と同じ）。

**⑤ note**：公式の投稿APIは今回確認できなかった。アフィリエイトは Amazon 以外が不明確。**不採用**。

### 1-3. Google の方針（AIで書くときの前提）
- 生成AIの利用自体は禁止されていない。問われるのは品質。**ランキング操作が主目的の大量生成は「スケール化されたコンテンツの不正使用」のスパムポリシー違反**になりうる。価値を足さずに多数のページを作ると該当しうる（Google 検索セントラル）。
- 公開前に人が全内容を事実確認することが求められている。人の監督なしに大量の文章を生成するのは「労力がほとんどない」と評価される、との記載もある（品質評価者ガイドラインの趣旨。検索結果の要約による）。
- 「誰が・どう作ったか・なぜ作ったか」（Who / How / Why）：執筆者表記を正確に。**架空の執筆者プロフィールは欺瞞**と明記。AIの関与は、読者が気にしうる場合に開示することが勧められている（AIを著者として表記するのは最適ではないとされる）。
- → **AI全自動公開は技術的には可能だが、「検品合格＋オーナーの最初の10本の確認」を残すのが安全**。検索クエリの言い換えごとにページを量産することも避ける（ガイドに明記）。

### 記事ごとの設計
- 冒頭に PR表記（タイトル直下）、「YYYY年MM月DD日時点」、公開日・更新日の両方を表示。
- 出典を記事末に一覧化（公式URL）。数字は公式ページを目で確認した記事だけ公開。
- 構造化データは Article/BlogPosting を JSON-LD で入れる（Google 推奨形式）。`author.url` で執筆者ページ（運営者情報）に紐付けると推奨されている。
- 個別商品の推奨・利回りの断定をしない。試算には「仮定・元本保証なし」。
- サイトマップを作成し Search Console に送信（必須ではないが発見が早まる場合がある）。Core Web Vitals の目安は LCP 2.5秒以内・INP 200ms未満・CLS 0.1未満（Google）。

## 5. 結論：おすすめの1案と最初の2週間（質問6）

### おすすめ：静的サイト（Astro）＋Cloudflare（Workers Static Assets）＋独自ドメイン（.com）
理由
1. **AIが git push だけで公開まで完結する**。通信先は既に使っている github.com のみで、新しい秘密情報が要らない（WordPress は、ドメインの許可・Basic認証のシークレット・サーバーの国外制限など、確認事項が多い）。
2. 費用は実質ドメイン代のみ（Cloudflare は無料。ドメイン年額は**要見積**）。
3. 保守が少ない（推測）。検品→公開の流れを、リポジトリのブランチ運用でそのまま再現できる。
4. ASP広告・PR表記・構造化データを自由に実装できる（GitHub Pages のような商用規定の懸念を避けられる。Cloudflare の規約は**要確認**）。

弱点：管理画面がない。オーナーが画面で直接編集したい場合は不向き。その場合の代案は **②エックスサーバー（月990円〜）でWordPress**（初期にREST APIの設定確認が要る）。

3. **運営者情報と監修**：会社名・連絡先をどこまで公開するか、FP・税理士の監修を入れるか（費用は要見積）。
